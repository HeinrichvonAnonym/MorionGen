# Motion retarget pipeline

This package converts AnDy, COMFI, and HiPHI motions to fixed-profile SMPL-X
archives with full 15-joint MANO poses per hand. The authoritative runtime
configuration is `config/motion_retarget.yaml`.

```bash
scripts/setup_motion_retarget.sh
scripts/run_motion_retarget.sh inventory --dataset andy
scripts/run_motion_retarget.sh extract --dataset andy --profile male_178 --resume
scripts/run_motion_retarget.sh validate --dataset andy --profile male_178
scripts/run_motion_retarget.sh render --dataset andy --profile male_178
scripts/run_motion_retarget.sh summarize
```

`--input-mode` can override the dataset default for a run; the override is
included in the resumability hash. Additional `gender + height_m + betas`
profiles can be added under `profiles` in the YAML without changing code.

Native sources take priority: Qualisys markers with GVHMR then Xsens fallback for AnDy,
aligned JCP mocap for COMFI, and 55-joint BVH for HiPHI. GVHMR is an explicit
video mode for AnDy and an automatic fallback after failed COMFI mocap IK; its
official preprocessing and predictor are used without the demo's optional
render pass. For AnDy, GVHMR also estimates video-to-mocap time offset from
22-joint SO(3) motion energy; low-confidence estimates stay at zero and are
reported as such. AnDy and COMFI hands come from WiLoR video inference; HiPHI
hands are retargeted from its native finger chains. Missing video observations
remain invalid even when the playable pose is temporally imputed.

The `source_native` virtual profile is resolved per sequence. It reuses complete
source SMPL-X gender/height/betas when present; otherwise it uses actor gender
and height with 16 zero betas. Only missing actor metadata expands to the two
configured reference profiles. AnDy automatic body fallback order is Qualisys,
GVHMR, then Xsens.

The isolated AnDy/HiPHI full batch is controlled by:

```bash
scripts/run_motion_retarget_andy_hiphi_source_native.sh preflight
scripts/run_motion_retarget_andy_hiphi_source_native.sh pilot
scripts/run_motion_retarget_andy_hiphi_source_native.sh start
scripts/run_motion_retarget_andy_hiphi_source_native.sh status
```

It fixes the output root, excludes COMFI, assigns one worker to each configured
physical GPU, and keeps its ledger, inventory, manifest, caches, and reports
independent from previous pilots.

HiPHI inventory uses the release-provided `motion_to_part.csv` joined with
`hiphi_metadata.csv`, excluding `__mirror` rows without decompressing the 32
archives. Older releases without those indexes fall back to cached streaming
tar listings. Motion payloads are always extracted one member at a time.

Each output is an atomic compressed NPZ under the configured 4T output root.
`poses` is the 165-dimensional SMPL-X view and `pose_aa_smplsim` is the
156-dimensional body-plus-hands MuJoCo view. `source_motion_scale` is applied
before the rigid `source_to_canonical` transform. The SQLite ledger and JSONL
manifest retain config, input, and model hashes.

Schema-v2 outputs also contain the actual continuous trajectory, not only
sampled frames: translation uses a quintic Euclidean B-spline and every local
rotation uses a sign-continuous quaternion quintic B-spline normalized at
evaluation. The open-domain representation and validation contract are C4.
Body, WiLoR hands, and native HiPHI hands are projected
before their marker/JCP/FK quality gates are evaluated; knots and coefficients
are stored in the NPZ and checked by `validate`.
The input hash combines every archive actually used by the selected modality
(including video, calibration, and metadata). WiLoR/GVHMR caches are named by
independent input/model fingerprints, so a changed asset cannot silently reuse
an older visual inference result.
Model dependency hashes include missing/present state, so outputs made before a
WiLoR or GVHMR checkpoint arrives are automatically regenerated by `--resume`
after the asset becomes available. The same hash also covers the retarget core
and isolated inference workers, preventing a code change from silently reusing
an output produced by older extraction logic.

MuJoCo validation is kinematic only. It independently compares SMPL-X joints
against MuJoCo body transforms and reports joint-limit, contact, SMPL-X mesh
ground penetration, collision-proxy ground penetration, and self-contact
statistics. It does not claim controller or dynamics tracking.

The isolated HiPHI rigid-object v4 gold sample uses schema v5 and is launched
with:

```bash
export MOTION_RETARGET_OUTPUT_ROOT="$PWD/develop_logs/test_runs/hiphi_object_v4_gold_windows"
scripts/run_motion_retarget_hiphi_object_pilot_v4.sh extract \
  --sequence Cause_to_move_in_place-turn_0143 --pilot-contact-windows --no-resume
scripts/run_motion_retarget_hiphi_object_pilot_v4.sh validate \
  --sequence Cause_to_move_in_place-turn_0143 --mujoco
scripts/run_motion_retarget_hiphi_object_pilot_v4.sh render \
  --sequence Cause_to_move_in_place-turn_0143
```

Short-window archives declare `solver_pilot_frame_mask` and can only reach
`pilot_windows_passed`; they are never counted as a full sequence. The object
SE(3) is read-only. Human deltas are optimized directly as quintic B-spline
controls, with per-side palm 6D Jacobian audits, a 5 mm connected-surface
correspondence bound, per-side augmented-Lagrangian state, and a bounded
root/lower-body fallback. The exact optimization knots and delta controls are
stored alongside the exact delivered C4 interpolation archive.

`render` produces the actual deforming SMPL-X surface mesh from model vertices
and faces. It does not visualize MuJoCo's box/capsule collision model. The
overlay reports `L/R HAND: OBS` for valid MANO observations and `PRIOR` for
smooth playback-only imputation, so missing video hands cannot look like
measured data during visual review. MuJoCo remains an independent validation
pass and its contact/penetration metrics stay in the JSON report.
Schema-v5 object renders use three panes: full body, hands/object with the raw
BVH hand proxy and source/target palm frames, and an independent right-hand
close-up. The overlay also reports the active 5 mm surface-remap distance.

The setup script first requests the GVHMR project's documented Google Drive.
If Drive is quota-limited, it falls back to the immutable 4DAnyone companion
release revision used with the unmodified GVHMR inference stack. All four
fallback files are pinned by exact size and SHA-256 before installation.
